## 三、为什么跳过（5 条理由）

### 理由 1：原计划的立论不成立

原计划说"41 处各清各的、留痕率低、风险高"。实测：**82% 已有日志、0 处禁用守卫、0 个已知 bug**。

### 理由 2：统一入口本身不产生收益，只产生风险

按"纯收口、0 行为变化"的做法（`clear_pending` 只置 null + 条件日志），批 1 那 17 处**全部是 `decided`（玩家已表态继续结算）→ 按 Q8.1=B 不写日志**，等于：

> 改了 17 处响应栈附近的代码，日志一行没增加，行为一模一样。

**净收益 ≈ 0，风险 > 0**。

### 理由 3：真正需要日志的场景，现有范式已覆盖

代码里已有正确示范（`do_action` 入口 24505 一带）：

```js
if (game.pending_event_step && !isStepOwnAction &&
    faction_of_nation(game.pending_event_step.nation) === side) {
    game.pending_event_step = null
    game.log.push('【美国】《××》分步结算被中断，剩余步骤作废')
    finish_event_card(...)
}
```

即"玩家做了无关动作 → 放弃挂起 → 清空并写日志"。凡是会被**别人的动作**顺带清掉的挂起，都已经按这个范式写了日志；剩下没日志的都是"自己结算完顺手清"，本来就有结算日志。

### 理由 4：静态扫描不可靠，规模评估靠不住

本轮核查中发现：靠正则猜"清理点属于哪个函数"**误判率很高**，抽样 3 处核实 2 处误判：

| 扫描报告 | 实际位置 | 判定 |
|---|---|---|
| `faction_of_nation()` 里清 `pending_event_step` | `do_action` 入口的中断守卫 | ❌ 误判（且它已写日志，是正确范式） |
| `refresh()` 里清 `delegate` | `next_nation` 动作里（17321 委托作废） | ❌ 误判 |
| `refresh()` 里清 `su_17817_pending` | 17817 结算分支 | ❌ 误判 |

既然"哪些是隐式清理"都数不准，就不该按这个清单动 60 处代码。

### 理由 5：成本收益比不划算

| 方案 | 工时 | 眼前收益 | 风险 |
|---|---:|---|---|
| 统一收口（全 60 处） | 5 h | 可维护性（延后兑现） | 中（响应栈时序） |
| 只高频 35 处 | 3.5 h | 同上 | 低-中 |
| **审计 + 只补确凿缺日志处** | 2.5 h | 直接（可查） | ≈0 |
| **跳过（本决议）** | 0 | — | 0 |

在"0 已知 bug + 82% 已有日志"的前提下，连审计的边际收益也不高——真出问题时按 §六 的手工方法排查更快。

## 五、什么情况下重启 D8

满足任意一条，建议重新评估（而不是直接照原计划做）：

1. **"窗口莫名消失"连续出现 2 次以上**，且日志无法定位是谁清的
2. **响应栈重构**（`REFACTOR_RESPONSE_STACK.md` 里的后续阶段）——那时才有必要统一入口
3. **新增一类挂起机制**，且需要跨 3 个以上函数清理（此时先按 `rtt-pending-suspend` 建，再考虑收口）
4. 清理点数量显著上升（如从 60 处涨到 80 处以上）

## 六、临时排查方法（不依赖 D8 也能查）

挂起窗口"凭空消失"时的最快路径：

1. **在 `do_action` 入口加诊断打印**：每次动作打印 `side` / `current_nation` / 各挂起字段是否存在
   （对照"动作进来前 vs 进来后"，一眼看出是哪个动作清掉的）
2. **搜清理点**：`grep -n "game\.pending_\w* = null" rules.js`，按字段名缩小范围
3. **判身份基准**：确认该清理守卫用的是 `side` 还是 `current_nation`（见 `rtt-pending-clear-side` skill）
4. **白名单**：若日志显示"动作根本没被受理"，转查 `build_actions`（见 `rtt-pending-whitelist-deadlock`）
