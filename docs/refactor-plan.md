# 重构方案（不是重写）— 分层重构 + 客户端 2.0

> 决策文档，2026-11-02。回答一个问题：**在现有项目上重构，还是重做 2.0？**
> 结论先行：**不整体重写。走"内核骨架重构 + 客户端整体换代"，用 Phase 0-4 分轨推进。**

---

## 0. 一句话结论

这套工程的**真正资产是规则判定口径**（446 张卡 + 7,332 行踩坑档案 + 584 个可执行测试），
不是代码结构。结构确实烂，但烂在**骨架**（挂起模型、动作注册、id 口径、刷新方式），
而骨架可以**一层一层换**，规则语义一行不用重推。

> **重写 2.0 = 把这套口径重新推导一遍**，而它无法枚举 —— 只能等玩家再报一遍 bug。
> **分层重构 = 换骨架、换脸，保留口径。**

## 2. "底层没搭好"的四个真病灶（都有实证）

这两周修的 bug **不是个案，是同一批结构缺陷反复发作**：

| 病灶 | 具体事故（近两周） | 是否结构性问题 |
|---|---|---|
| **① 挂起状态无统一模型**（25 个 `pending_*` 各自为政） | 17828《百团大战》×17553《抗日义勇军》让权 → 双向死锁；15410《武士道》×"空军免死"抢客户端窗口；《大清洗》窗口漏给轴心 | ✅ 会持续复发 |
| **② 双份判定源** | `view.actions` 白名单 vs 实际 handler（漏登记=静默丢弃）；候选计算 vs 点击判定（15355 对象 vs id → 服务端对、客户端点不动）；`run` 返回 `ok:false` 被静默吞掉 | ✅ |
| **③ id / 阵营口径三套** | 实例 id vs 面 id（状态卡记账失效）；`active`(阵营) vs `current_nation`(国家)；`side` vs `my_nation`（专属窗口漏给对手） | ✅ |
| **④ 全量重绘 + 巨型单文件** | 每次动作广播整份 view，客户端清空重建；高亮动画导致 40 单位时帧率 −65% | 工程性 |

**推论：①②③ 靠"修单卡"永远修不完**（两周内同类修了 6 次），但它们**不需要改规则语义**，只需换骨架。

## 3. 重写 vs 重构：三笔账

| 维度 | 大爆炸 2.0 | 分层重构（本方案） |
|---|---|---|
| 规则口径 | 从零重建 446 卡 + 7.3k 行裁定 | **原样保留**，584 测试守门 |
| 回归风险 | 极高（无人能枚举"应该是什么"） | 低（每阶段有快照 + 测试网） |
| 上线节奏 | 数月空窗，期间 bug 无处修 | **持续可发布**，随时可回滚 |
| UI 包袱 | 一次清掉 | 同样能清（Phase 2 就是 2.0 UI） |
| 前提 | 规则要换 / 平台要换 / 团队重写 | **规则稳定、痛点在一致性与体验** ← 你的情况 |

## 4. 路线：三轨并行，先骨架后界面

### Phase 0 · 基线冻结（约 1 周，**先做这个，其余才有意义**）

| 动作 | 产出 |
|---|---|
| 抓 `view` / `actions` / `query` 的 JSON 快照 + schema（目前只是隐式约定） | `tools/fixtures/view_snapshot_*.json` |
| 584 脚本纳入一键回归 + 已知问题白名单（当前 22 个） | `tools/_run_smoke_report.js`（已有，补白名单清单） |
| 线上/本地基线核对脚本 | `tools/_check_online_version.js`（已写） |

**验收**：任何重构后，快照 diff 必须为 0 或"已知变更清单"内。

---

### Phase 1 · 内核骨架重构（2–3 周，**行为零变化**）

| # | 改动 | 消灭的病灶 | 验收 |
|---|---|---|---|
| 1.1 | **action 注册表化**：`{name, side, gate, handler}` 表驱动，`view.actions` **自动生成** | ② 静默丢弃 / 漏阵营 | 108 个 action 全部迁移；"每个 action 必须能在某状态下被授权"的结构断言 |
| 1.2 | **单一挂起队列**：25 个 `pending_*` → `queue:[{kind, owner_side, priority, ctx, resolve}]`；`priority` 显式（**必须回答 > 可选**） | ① 互锁死锁 / 窗口互抢 | 结构断言：**任何挂起存在时，必须存在至少一个能回答它的 action**（这条断言能提前抓住 17828/15410 两类事故） |
| 1.3 | **id / 阵营规范**：`piece_id`(实例) / `face_id`(面) / `piece_nation` / `piece_type` 四字段固定；禁止 `nation/type` 别名 | ③ 幽灵部队、记账失效、漏阵营 | 静态检查：view 里窗口类字段必须带 `=== side` 判定 |
| 1.4 | **候选与执行同源**：`can_*` 原子被 `need` 计算与 `run` 共同调用 | ② 影子盘面不同步（15315 连带空军） | 每张分步卡一条"候选 == 实际可执行"断言 |

> 迁移顺序建议：**1.1 → 1.3 → 1.4 → 1.2**（1.2 改动最深，放最后，前面几步会大幅降低它的难度）。

---

### Phase 2 · 客户端 2.0 垂直切片（2–3 周，**可与 Phase 1 并行**）

- 技术栈：Vite + TypeScript + 组件化 + 响应式（替代 10,854 行全局脚本）；
- **不碰规则**：只消费同一份 `view` 契约；
- 第一个切片：**地图（复用 `layout.js` 坐标）+ 手牌 + 统一询问框**；
- 双跑：`?ui=next` 切换，新旧并排比对（截图 + jsdom 断言）；
- 移动端从第一天就按**触控目标 ≥44px / 底部抽屉 / 手牌横滑**设计（详见 `docs/ui-mobile-guide.md`）。

---

### Phase 3 · UI 迁移收尾 + 传输优化（增量）

- 面板逐个迁移（阶段条、桌面卡、日志、调试面板），旧入口保留到等价性通过；
- `view` 改**增量 patch**（先加兼容层），解决大局面全量重绘卡顿；
- 目标：`play.js` 退役，`play.css` 由组件样式取代。

---

### Phase 4 · （可选）6 人版状态模型

- `active`(阵营) + `current_nation`(国家) → **seat（座位）模型**；
- 这一步才真正动数据模型，但此时已有注册表 + 挂起队列 + 快照，风险可控；
- 与 skill `rtt-delegate-flip` 里的"两级模型"说明对齐。

---

## 5. 红线（重构期间不要做的事）

1. ❌ 不改 `cards.js` 的数据结构（446 张卡的键名/含义）；
2. ❌ 不重排 `layout.js` 坐标（生成物，牵动算子定位 + 多组 jsdom 测试）；
3. ❌ 不一次性重写 446 张卡的实现形态（按 Phase 1.4 的 `can_*` 逐步收口）；
4. ❌ 不做"顺手改名/格式化"式大 diff（会淹没真实变更，破坏快照对比）；
5. ❌ 不在 Phase 0 之前动任何核心函数。

---

## 6. 什么时候才真该做 2.0？（决策阈值）

同时满足 **≥3 条**再考虑重写：

- [ ] 规则语义要换骨架（不是补卡，而是换玩法）
- [ ] 要跨平台（原生/桌面端），且有独立前端团队
- [ ] 现有测试资产不可信/跑不起来（你现在有 584 个能跑的）
- [ ] 商业模式要求数月内整体换皮（重构无法一次交付"新外观"）
- [ ] 团队无人熟悉现有代码，学习成本 > 重写成本

**当前判断：都不满足**（规则稳定、测试可用、痛点集中在一致性与体验）。
