## 0. 为什么要重写这一版（2026-09-24）

v1.0 把 23 张卡当成"事件卡"一起实现了，其中混进了
**15305–15312 这 8 张，它们其实是【↑ 增强卡(ECHO)】**
（经像素识别确认，见 `docs/card-icons.md`）。

按"**先仅实现事件卡，其余卡之后再说**"的要求：

- 这 8 张增强卡的**实现已清除**（从 `EVENT_EFFECTS` 配置移除）
- `event_effect_of()` 收窄为**只认 `EVENT`**
- `play_card` 的分支收窄为**只处理 `EVENT`**
- 测试相应改为覆盖 15 张事件卡，并断言 8 张增强卡**没有**配置

> **教训**：卡的类型决定它的**时机语义**，
> 不能因为"效果长得像"就合并实现。
> 增强卡是"对应时机打出、不占名额"，
> 与事件卡"出牌阶段打出、占名额"是两回事。

## 1. 分层架构（你的要求：相同底层逻辑要复用）

```
┌─────────────────────────────────────────────────┐
│  卡类型层（决定【时机语义】）                     │
│    BASIC   出牌阶段，占名额                      │
│    EVENT   ! 出牌阶段，占名额   ← 本文件         │
│    ECHO    ↑ 对应时机，不占名额  ← 待实现        │
│    RESPONSE ? 响应触发          ← 待实现         │
│    STATUS  ⇈ 留桌面持续生效      ← 待实现         │
│    ECON    兵器 经济战           ← 待实现         │
├─────────────────────────────────────────────────┤
│  各类型的「配置 + 执行器」                        │
│    EVENT_EFFECTS + resolve_event_card            │
├─────────────────────────────────────────────────┤
│  ★ 原子操作层（所有类型共用，禁止重复实现）      │
│    can_build_at   / build_piece                  │
│    can_recruit_at / recruit_piece                │
│    eliminate_piece                               │
│    do_battle      / seize_air                    │
│    grant_supply                                  │
└─────────────────────────────────────────────────┘
```

**为什么用函数组合而不是类继承**：原子操作都是**无状态纯函数**，
直接调用比继承更简单，也没有 `this` 绑定的坑。
新增任何卡类型都**不要**重新实现"征召/建设/消灭/战斗"，
一律调用原子操作层。

**已实现的类型对本层的依赖**：

| 类型 | 依赖的原子操作 |
|---|---|
| BASIC (5) | `build_piece`、`do_battle`、`seize_air` |
| EVENT (15) | 全部（经 `EVENT_EFFECTS` 配置） |
| ECHO (8) | 待实现，将来同样复用全部 |

## 2. 前置：两条规则（玩家 2026-09-23 确认）

### 2.1 征召 vs 建设

规则书五章只有两行带"**对于建设部队：**"前缀：

| | 建设 | 征召 |
|---|---|---|
| 地形限制（陆军陆地/海军海域） | 有 | **有**（共同） |
| 不能有敌方/本国部队 | 有 | **有**（共同） |
| 位置要求（大本营/邻接补给） | **有** | **无** |
| 新部队处于补给状态 | **是** | **否** |

**佐证**：《史末资加强对英关系》"在\<非洲南部\>征召陆军，**其在本回合内始终处于补给状态**"——
正因为它默认断补，才需要这张卡补上。

"征召不保证补给"**不需要额外机制**：补给每次由 `compute_supply` 重算，
征召的部队若恰好邻接补给部队照样有补给，只是**不强制**。
需要强制的走 `grant_supply()`。

### 2.2 消灭（玩家 2026-09-24 重新定义）

- **直接移除**指定地区的 1 支敌方部队
- **不需要**相邻发起单位、**不检查**补给状态
- **不受中立限制**（规则书明确中立方"可以执行卡牌效果中的消灭"）
- 与"发起战斗"是两条不同的路径
- 空军仍不能作为消灭的**目标**（与 `do_battle` 口径一致）

**两条 2026-09-24 新增/修正的规则**：

| 规则 | 内容 |
|---|---|
| **连带消灭空军** | 触发消灭时，若有与被消灭单位**同国**的空军在同一地区，则**一并消灭**（不论几支，全部移除） |
| **不触发参战** | 若被消灭方中立，**不会**触发参战 |

#### 连带消灭：是【同国】不是【同阵营】

法国空军只跟着法国部队走，**不会**因为同属同盟就替英国部队陪葬。
这与 `do_battle` 的代受判定（`air_nation`）口径一致。

```
地区上有：德国陆军(目标) + 德国空军A + 德国空军B + 意大利空军C
消灭德国陆军 -> 连带移除 德国空军A、B；意大利空军C 不受影响
```

#### 不触发参战：与 do_battle / seize_air 相反

| 动作 | 被攻击方中立时 |
|---|---|
| `do_battle`（发起战斗） | **会**结束中立 |
| `seize_air`（夺取制空权） | **会**结束中立 |
| `eliminate_piece`（消灭） | **不会**结束中立 |

即消灭**不是**"攻击"。`eliminate_piece` 里**故意不调用**
`maybe_end_neutral_by_attack`。

## 4. 配置与执行

### 4.1 配置结构

```javascript
'15319': {
    name: '增加英联邦支持',
    actor: '英国',                       // 执行国
    cost: { discard: 2 },                // 弃牌代价（当前无卡使用）
    steps: [{ op:'recruit', type:'army', spaces:[...] }],
},
'15322': {
    name: '法国海军',
    actor: '法国',
    choice: [                            // 二选一
        [{ op:'build', type:'navy' }],
        [{ op:'battle', kind:'sea' }],
    ],
},
```

### 4.2 step 字段

| 字段 | 含义 |
|---|---|
| `op` | `recruit` / `build` / `eliminate` / `battle` / `ongoing` |
| `type` | `army` / `navy` / `air` |
| `spaces` | 合法地区；省略则全图推举 |
| **`pick`** | **需选几个地区**（默认 1）。>1 时对选中的地区**各执行一次**（2026-09-24 新增，见 §4.5） |
| `kind` | battle 专用：`land` / `sea` |
| `grantSupply` | 征召后授予本回合补给 |
| `useNewPiece` | battle 用刚创建的部队发起 |

### 4.3 actor：英国 vs 法国

法国委托给英国（`delegate_of_nation('法国') === '英国'`），
所以英国玩家手里的卡可能操作**法国部队**。

判定规则（逐张核对）：
- 卡名含"法国"，或正文以"法国"开头 → 法国
- 否则 → 英国

### 4.5 多选（pick > 1）

卡面"在 A、B、C 之**二**征召"这类表述需要从候选中选**多个**地区。
step 加 `pick: N`，执行器对选中的地区**各执行一次**操作。

```javascript
'15326': {
    name: '自由法国同盟',
    actor: '法国',
    steps: [{ op:'recruit', type:'army', pick: 2,
              spaces: space_ids_of(['西欧','非洲北部','非洲南部']) }],
},
```

- 候选数 `> pick` → 必须由玩家指定（未指定则 `pending` 等待）
- 候选数 `== pick` → 自动全选，不问
- 参数：卡片单 step 用 `arg.picks = [id1, id2]`；多 step 用 `arg.picks[i] = [...]`

### 4.6 法国卡的战斗/建设必须用【法国】单位（2026-09-24 检查确认）

**结论：当前实现正确。** 两条依据：

1. `battle_initiators(game, nation, space)` 里用
   `game.piece_nation[p] !== nation` —— 按**国籍**严格筛选，
   法国卡的 `actor='法国'`，因此只列出**法国**单位。
2. `resolve_event_card` 传给 `do_battle` 的第一个参数是 `eff.actor`，
   即 `'法国'`，不是持有国 `'英国'`。

配套行为：
- 敌我判定用**阵营**（`faction_of_nation('法国') === 'allies'`），正确
- 法国不在 `NEUTRAL_RULES` 名单，`neutral_attack_check` 放行
- 法国攻击苏联不会触发苏联参战（苏联只因德/意攻击而参战）
- 建设/征召产出的部队国籍 = `actor`，即法国部队

测试 §33 专门锁住：法国单位与英国单位同时可作发起单位时，
法国卡指定英国单位 → **拒绝**；指定法国单位 → **成功**。

### 4.4 执行流程

`resolve_event_card(game, nation, card_id, arg)`：

1. **缺参数** → `{ok:true, pending:true, need:{...}}`，**不弃牌不结算**
2. **代价**：弃置 N 张手牌（不含本卡）
3. **依次执行**各 step

参数：`space`（单步地区）、`spaces[i]`（多步）、`choice`（选项索引）、
`piece`（目标算子）、`from`（发起单位）、`cards`（弃牌选择）。

客户端用 `query('event_targets', {card})` 查询需要什么。
