## 1. 规则原文（简化规则书 第三节）

> **补给**：在游戏过程中，部队可能因为推进过快、被敌军包围或海上封锁而陷入补给不足的状态。
>
> - **陆军**满足以下条件之一，则处于补给状态：
>   - 位于补给点（地图上标记 **★** 的地区）
>   - 与处于补给状态的**本国**部队相邻
> - **海军**满足以下**全部**条件，则处于补给状态：
>   - 与处于补给状态的**本国**部队相邻
>   - 与**本国或友军**的陆地部队相邻
>
> **补给阶段**：将**当前回合国**不处于补给状态的部队移除

原文未覆盖的部分（17549 放宽、临时补给、建设条件）由 §2 / §3 的玩家口径补齐。

## 2. 补给状态（2026-10-23 定稿）

### 2.1 种子：**只有 ★**

```
★ = data.spaces[i].supply（12 个）+ supply_override（可"仅对某国/某阵营"）
```

- **★ 对任何站上去的国家都生效**：美国陆军站在英国★（西欧）上，也能获得补给，并以该 ★ 作为**美国**链的起点。
- 除 ★ 之外，**没有任何隐式种子**（没有"大本营自动补给""某国天然补给"）。

### 2.2 「补给状态」≠「补给源」——两个概念必须分开

| 概念 | 含义 | 用途 |
|---|---|---|
| `in_supply[S]` | 这支部队**当前是否处于补给** | 决定补给阶段会不会被移除 |
| `can_source[S]` | 这支部队**能不能作为别人「连回源」的依据** | 别人判断 A 条件时用 |

| 补给怎么来的 | `in_supply` | `can_source` | 说明 |
|---|---|---|---|
| 站在 ★ 上（`base`） | ✅ | ✅ | 真正的源头 |
| 从 `can_source` 邻居链传下来（`chain`） | ✅ | ✅ | 链上的活水 |
| 卡牌授予（`supply_granted`，如史末资） | ✅ | **❌** | 只是"这一支被照顾"，不是源 |
| 光环 `supply_immune`（15346 自由法国、17838 等） | ✅ | **❌** | 同上 |
| 光环 `space_immune`（8601 远东共和国） | ✅ | **❌** | 同上 |
| echo（15207 空投补给，本回合全体德国） | ✅ | **❌** | 同上 |

> **判据（玩家原话）**：「这些提供的是对某单位临时补给状态，不是补给源。」

### 2.3 陆军

相邻格有 **`can_source` 且补给中**的部队，归属为：

- **本国**，或
- **17549 共享组内**（英 / 法 / 美）

### 2.4 海军

| 条件 | 内容 | 17549 |
|---|---|---|
| **A**（来源） | 相邻格有 **`can_source`** 的补给部队 —— **不限兵种** | ✅ 可组内 |
| **B**（港口） | 相邻格有 **陆军** —— 不要求该陆军自身补给 | ✅ 可组内 |

两条**分别**满足即可，不要压在同一支部队上。

### 2.5 全补给国家（法国 / 苏联）

- **随卡/光环存在与否**：拥有 15346《自由法国》时法国部队恒补给；拥有 17838 时苏联恒补给；卡离场即失效
- 这类部队 **`in_supply = true` 但 `can_source = false`**
  - 自己**不要求连 ★**（符合卡面）
  - **不能**给别人当 A 的来源
  - **可以**满足 B（B 只要求"有陆军"，不要求补给）
- 光环按 scope 生效（15356 限定 `navy` + 指定海域）

### 2.6 断补结算

- 只移除**当前回合国**的断补部队
- `protect` 修饰器（如马奇诺）可豁免
- 移除后依次触发：17512 计数 → 15216 总体战损耗 → 响应卡
- 结算后 `refresh(game)`（海峡控制权/连通性会变）

## 3. 建设口径（与补给的差异只有 **A 的国籍**）

| 判定 | A（来源 / 连回源） | B（陆地部队 / 港口） |
|---|---|---|
| 补给 · 陆军 | `can_source` 的 **本国 / 组内** 部队 | — |
| 补给 · 海军 | `can_source` 的 **本国 / 组内** 部队 | 陆军，**本国 / 组内** |
| **建设 · 陆军** | 相邻有 **`in_supply`** 的 **仅本国** 单位（或本国大本营） | — |
| **建设 · 海军** | `can_source` 的 **仅本国** 部队 | 陆军，**本国 / 组内** |

**一句话**：

> 17549 对 **B（港口/陆地部队）** 两处都生效；
> 对 **A（补给来源）** 只在【补给结算】生效，【建设】不生效。

### 3.1 四例验证（玩家 2026-10-23 给出）

盘面：17549 已开；北海有英国海军；北大西洋有英国海军；西欧有英国陆军；美国本土有美国陆军。

| # | 操作 | 结果 | 依据 |
|---|---|---|---|
| 1 | 美国在**西欧建陆军** | ❌ | 建设陆军要「相邻有补给中的**本国**单位」，西欧旁无美国单位 |
| 2 | 美国在**北海建海军** | ❌ | 建设海军 A 要「相邻有 `can_source` 的**本国**部队」，北海旁无美国部队 |
| 3 | 北海的**美国海军**补给 | ✅ 补给来自美国本土陆军 | 链见下 |
| 4 | **北大西洋有美国海军** → 北海建海军 | 开 17549 ✅ / 不开 ❌ | A 由北大西洋美国海军满足；B 开时用西欧英国陆军，不开时无美国陆军 |

第 3 例的链：

```
美国★（美国格，base）
  └─ 美国陆军@美国                     base
       └─ 英国海军@北大西洋              chain｜A=美国陆军(组内) B=美国陆军(组内)
            └─ 美国海军@北海             chain｜A=英国海军(组内) B=英国陆军@西欧(组内)
```

第 4 例反证：北海能建海军，唯一差别是 **A 必须由本国部队提供**（北大西洋的美国海军）。

### 3.2 建设陆军

- **本国大本营**：直接可建（大本营可能被 15344 改判，走 `effective_home_base`）
- 其它陆地：**相邻有 `in_supply` 的本国单位**

### 3.3 建设海军

另需：海域地形、无敌军、槽位空闲（每国每格陆/海合计 1 支）。

## 4. 算法：不动点迭代 + can_source

```
种子：
  站在 ★ 上的部队      -> in_supply=true, source='base',     can_source=true
  supply_granted      -> in_supply=true, source='granted',  can_source=false
  supply_immune 光环  -> in_supply=true, source='aura',     can_source=false
  space_immune 光环   -> in_supply=true, source='aura',     can_source=false
  echo 空投补给        -> in_supply=true, source='echo',     can_source=false

循环（直到无新增，guard<200）：
  陆军：相邻有 can_source 且 in_supply 的本国/组内部队 -> in_supply=true, source='chain', can_source=true
  海军：A（相邻有 can_source 且 in_supply 的本国/组内部队，不限兵种）
      且 B（相邻有陆军，本国/组内）
      -> in_supply=true, source='chain', can_source=true
```

**为什么必须不动点**：`"与处于补给状态的部队相邻"` 本身是递归定义，普通 BFS 会按遍历顺序出错。

复杂度最坏 O(n²)，部队上限约 40~60，实测 0ms。

## 5. 实现

```javascript
compute_supply(game, conn_snap)   // 纯函数，不改 state
// 返回 { in_supply: {pid:true}, sources: {pid:'base'|'chain'|'granted'|'aura'|'echo'}, can_source: {pid:true} }
```

- `conn_snap` 可复用 `compute_connections()`，避免重复计算
- 连通性**阵营私有**（海峡控制权影响）：海军只能走本方可用航道
- 建设与补给**共用同一套 A/B 判定**（收口在一个函数里，避免再次分叉）

## 7. 12 个 ★ 补给点

```
不列颠、西欧、莫斯科、意大利、中国东部、美国、
印度、澳大利亚、德国、乌克兰、日本、夏威夷
```

来源：`out/spaces_calibrated.json` 的 `supply:true`，编译进 `data.js`。
运行时可通过 `supply_override` 增删或限定国家/阵营（`docs/supply-points.md`）。

### 7.1 动态层 API 与语义（2026-10-23 核对）

```js
add_supply_point(game, space, factionOrNation)     // factionOrNation = null | 'axis' | 'allies' | 国家名
remove_supply_point(game, space, factionOrNation)
reset_supply_point(game, space)                    // 删除整格 override，回落地图标定
```

| 调用 | `supply_override[space]` | 语义 |
|---|---|---|
| `add(sp, null)` | `{axis:true, allies:true}` | 两阵营都成为补给点 |
| `add(sp, 'allies')` | `{allies:true}` | 仅同盟 |
| `add(sp, '苏联')` | `{nations:{苏联:true}}` | **仅苏联**（同阵营他国也不算，且不回落地图默认） |
| `remove(sp, null)` | `{axis:false, allies:false}` | 对所有人失效（焦土 / 迁都） |
| `remove(sp, '苏联')` | `{nations:{苏联:false}}` | **只让苏联失效**，别国回落地图标定 |

**优先级**：国家维度 > 阵营维度 > 地图标定。

**大小写**：`'Axis'` / `'Allies'` 会被归一为小写阵营键（2026-10-09 修复的历史 bug：大写值会误落进国家维度，导致补给点对全阵营失效）。

### 7.2 2026-10-23 修复

`is_supply_point` 原实现里，只要"只设了国家维度"就 `return false`，于是
`remove_supply_point(sp, '苏联')` 会把**同阵营其他国家**也一并判为"不是补给点"
（静态★格子上，美国会被误判断补）。

现改为按 `nations` 里的值区分：

- 存在 `true` 条目 → 「仅对该国」→ 别国 `false`（且不回落）
- 全是 `false` 条目 → 「只对该国失效」→ 别国回落 `base`

宽松查询（省略 faction，供 UI 用）同步修正。

### 7.3 已知设计：补给点变更**永久不撤销**

`revert_status_ongoing` 里明确标注「15345/15347 supply_point_and_markers：A4① 永久，不撤销」，
17840 焦土 / 17845 迁都同样只写不撤。

即：**即使发动的状态卡后来离场，补给点的增删仍然保留**。
若某张卡的卡面要求"卡在才生效"，需另建 revert 分支（目前没有这种卡）。

## 10. 已知易错点

1. **同格不传递**：`get_connections` 不含自身格，同格友军互不接应（符合原文"相邻"）
2. **海峡会改变邻接**：`limited_connections` 把"经受控海峡连通"压成直接相邻（如 北海↔地中海），会同时影响补给链与建设判定
3. **写海军建设时不要用"模拟放置后跑 compute_supply"**：15346 光环会让新海军自身判为补给，绕过 A/B（这正是 `can_source` 分离后要单独处理的原因）
4. **`build_candidate_spaces` 会跳过所有海域**（该函数当前只服务苏联陆军），不要拿它算海军候选
