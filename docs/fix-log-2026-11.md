## 2026-11-11 · 17842《喀秋莎》未生效：after_land 窗口只认发起国本人（消除假窗口）

- **玩家报障**：「噶秋沙疑似未能实际生效，排查是哪里有问题。」→ 方案 A：
  卡面「发起陆战后」的主语是卡主本人，不是同阵营任一友方。
- **排查结论**：苏联**自己**发起陆战 → 喀秋莎完全正常（弃 1 张、发起陆战、
  移除剩余日军、次数消耗）。问题在**英国/美国发起陆战**时：
  `arm_status_instant` 按同阵营武装，把苏联喀秋莎塞进 `status_instant`，
  但 `status_window_ready` 的 owner 判据要求 `current_nation===苏联`、
  `status_instant_covers` 又因 `by≠owner` 不放行（`CROSS_NATION_STATUS_WINDOWS`
  不含 `after_land`）→ **假窗口**：亮着点不动，点了报「不能触发非本方的状态卡」，
  日军不动、代价不扣。与 #8（15432）、17543（雷达）同类。
- **改法**（详见 `docs/change-17842-katyusha-window.md`）：
  `arm_status_instant` 的 `table` 遍历里加
  `if (window === 'after_land' && own !== nation) continue`；
  `after_ally_battle`（卡面写"友方"）保持同阵营不动。客户端零改动。
- **影响面**：15253 闪电战 / 15245 俯冲式轰炸机 / 17842 喀秋莎 /
  17846 坦克运输 / 17848 正面攻击 —— 全是「本国发起陆战后」的卡，收紧后行为正确。
- **验证**：新增 `tools/_real_test_17842_katyusha.js` **20/0**（苏联发起可真实生效 /
  英国发起不入窗口 / 德国跨阵营发起不入窗口 / 17848 同款 / 静态守卫）；
  `_real_test_neutral_17900` 33/0（E6 按方案 A 反转）、`_real_test_17900_manual_finish` 28/0、
  `_smoke_air_retreat_restore` 72/0、`_smoke_seq` 52/0；
  `_smoke_su_status` 28/6 与 `test_basic_cards` 288/9 均经 HEAD 对照确认预存。
- **同日补修 · 17732 借用兼容**：玩家追问「对 17732 会有影响吗」—— 会。
  17732 让意大利借用德国状态卡，而德国 15253《闪电战》/15245《俯冲式轰炸机》
  正是 `after_land` 卡：收紧按 `own!==nation` 一刀切会让借用方发起陆战时该卡不被武装，

  改为把收紧下沉到**单卡**层并对「正被借用的那一张」放行

## 2026-11-11 · 17900《八月风暴》：涉及战斗的让权改为手动归还（要求无硬挂起）

- **玩家口径**：所有可能涉及战斗的让权都应手动归还而非自动归还，避免状态未正确触发；
  结束委托要求无硬挂起。17721 不涉战斗（只打状态卡）不改。
- **根因**：`use_armed_offer` 成功后 `refresh_armed_window` 扫手牌（17900 已离手）→
  `removeArmedWindow` → `clear_pending_armed_delegate` **自动归还**。而第二步
  `do_battle` 因日军空军挂起 `pending_battle`，战斗未结算、`after_land`（喀秋莎）
  窗口尚未武装 —— 委托提前结束、`current_nation` 提前回英国，状态窗口落在"别人回合"。
- **改法**（详见 `docs/change-17900-manual-finish.md`）：
  ① 新增 `armed_delegate_can_finish`（`played` + 无硬挂起清单）；
  ② 新增 `finish_armed_delegate`（清挂起 + 归还 + 移窗口）；
  ③ `refresh_armed_window` 对 special 只置 `played`、保留窗口；

     `pending_battle` 分支先返回 use/skip → "委托结束不了、战斗也打不完"双向死锁；
  ⑤ 战斗/响应/对方时点三处守卫放行 `finish_armed_delegate`，并加入
     `isSameMomentWindow` 豁免（否则被 `clear_armed_offer_for_side` 先清）；
  ⑥ `view` 下发 `played`/`can_finish`/`name`，客户端 `played` 时显示「结束委托」。

## 2026-11-11 · 17900《八月风暴》：补齐增强卡弃牌代价框（复用 17809 通用实现）

- **现象**：玩家报「缺失通用增强打出的弃牌框，复用其他苏联增强的弃牌代价实现，例如 17809」。
  实际表现：英国攻击<中国东北>后 17900 窗口弹出，点「打出」→ 服务端拒绝
  「需先选择弃置 1 张[建设陆军]」→ 窗口保留 → 再点还是被拒，**死锁**。
- **根因**：`maybe_arm_su_augstorm` 手工构造窗口时把 `cards[].cost` 写成了**数字**
  （`(eff.armed.cost && eff.armed.cost.discard) || 0`）。客户端
  `update_armed_offer_box` 读 `c.cost.discard` 得到 `undefined` → `dis=0` →
  不弹弃牌框直接发 `use_armed_offer{card}`；而服务端读卡配置 `ar.cost.discard=1`
  → 要求 `drop` → 收到空 → 拒绝。通用窗口（17809 等）下发的是 `ar.cost` 对象，故正常。
- **顺带修两处同源缺口**：
  ① `pending_echo_discard.card` 只传 `{id}`，标题渲染成「《undefined》」（影响所有
     armed 弃牌代价）；
  ② 服务端 `_picked` 只校验 `filter==='response'`，**缺 `'build'`** — 直接调 action
     可拿任意手牌替代「建设陆军」（客户端过滤只是摆设，违反判定同源）。
- **改法**（详见 `docs/change-17900-discard-modal.md`）：
  ① `cost: eff.armed.cost || {}` 原样下发对象；
  ② 补 `name: c.name`；
  ③ `_picked` 补 `filter==='build'`（BASIC 且 name=建设陆军）并按 filter 输出拒绝文案。
  客户端选牌 UI 零新增（`build` 过滤早已存在）。
- **验证**：新增 `tools/_dom_test_17900_discard.js` **19/0**（真 jsdom：窗口形状、
  按钮标注「弃 1 张」、点击弹框而非直发、标题无 undefined、只列 2 张建设陆军、
  确认后发 `drop`、服务端拒非法代价且窗口保留）；
  `_real_test_supp_su` 25/0、`_real_test_neutral_17900` 33/0、`_smoke_us_status3` 41/0、
  `test_basic_cards` 288/9 与基线一致；全量冒烟仅 2 个预存未登记失败。
